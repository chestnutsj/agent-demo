# SQL 优化

**永远不要只看 SQL 文本就推荐索引。** 同一条语句在两张统计信息不同的表上，最优计划可能
完全相反；文本层面看着"少了个索引"的查询，真实计划里往往是隐式类型转换或者中间列的范围
条件把复合索引截断了。

数据库访问只有 `mcp__dba_sql__sql_evidence` 这一个工具——没有 shell，也没有"随便执行一条
SQL"的入口。被优化的语句只会跟在 `EXPLAIN` 后面跑。

## 1. 取证

```
mcp__dba_sql__sql_evidence   { "sql": "<不带 EXPLAIN 的语句>" }
```

一次返回一份证据包：

1. `EXPLAIN FORMAT=JSON` 的完整计划；
2. 语句涉及的每张表（最多 4 张）的 `SHOW CREATE TABLE`；
3. 每张表的 `SHOW INDEX`；
4. 每张表的 `table_rows` / `data_length` / `index_length` / `update_time`。

需要真实耗时而不是优化器估算时加 `"analyze": true`。**`EXPLAIN ANALYZE` 会真正执行这条
语句**（MySQL 8.0.18+），对重查询先跟用户确认；它只对 SELECT 开放，DML 会被拒绝。

这一版只有这一个工具。需要别的语句（采样某列的区分度、看 `SHOW STATUS`）时，把语句给用户
执行、请他贴回来——和下面「手动接力」一样的做法。

## 2. 读计划

按顺序对照，先定位问题在计划的哪一行，再谈怎么改：

- `access_type`：`ALL` 是全表扫描，`index` 是全索引扫描，两者在大表上都是问题。
- `rows_examined_per_scan` 与最终返回行数的比值——扫 100 万行返回 10 行，说明过滤条件没走上索引。
- `used_key_parts`：复合索引只用上了前几列，往往是中间列用了范围条件。
- `filesort` / `temporary table`：排序和分组没能利用索引顺序。
- `attached_condition` 里出现 `cast(...)`：隐式类型转换，索引直接失效。

再拿证据包里的表信息校准：`SHOW INDEX` 的 `Cardinality` 决定了优化器会不会选这个索引——
区分度低的列建索引通常没用；`table_rows` 决定一次全表扫描到底是不是问题，几千行的表上
`ALL` 往往是最优解，对它提索引是纯粹的负收益。

## 3. 给建议（按代价从低到高）

1. **改写查询** — 消除函数包裹索引列（`WHERE DATE(created_at) = ...` 用不上索引）、消除隐式
   类型转换（字符串列传数字）、把 `OR` 拆成 `UNION ALL`、把大 `OFFSET` 分页改成游标分页。
2. **加索引** — 说明列顺序的理由：等值列在前，范围列在后，排序列跟在等值列之后。同时说明
   代价：写放大、占用空间，以及它可能让优化器改选更差的计划。先检查证据包里已有的索引，
   能靠调整已有索引的列顺序解决，就不要新建。
3. **改结构** — 分区、归档、冗余列。这类建议必须附带迁移影响；属于「结构变更」类目的部分
   （本版本未实现）只做说明，不给可执行的变更计划。

每条建议都要指明它对应计划里的哪个具体问题。说不出"因为计划里 X，所以做 Y"，就说明证据
还不够——回到第 1 步补。

## 4. 验证与交付

- **改写类**：改写后再调一次 `sql_evidence`，把两份计划摆在一起对比 `access_type` 与扫描行数。
  说"这样更快"而不给出改写后的计划，等于把验证的活推给了用户。
- **索引与结构类**：这个 agent 执行不了 `CREATE INDEX` / `ALTER TABLE`，也不该去执行——
  这是刻意的，不是故障。交回可直接执行的语句、预估影响（锁表时长、是否 online DDL）和
  回滚方式，由用户自己执行。

## 连不上数据库时：手动接力

工具返回内容以 `DBA_OFFLINE:` 开头时，表示这台机器连不到数据库。**不要重试，也不要凭 SQL
文本硬答。** 返回里的 `--- 请执行 ---` 区块已经把整份证据包需要的语句列好了：原样转述给
用户，说明每条是用来判断什么的，请他执行后把输出贴回来，再按上面第 2–4 步照常分析。

接力模式下的分析质量应当和直连时没有差别。
