# SQL 优化流程

五个阶段按顺序走完，缺一段不算完成。

## 阶段一：前置检查

先确认三件事再谈优化：数据库版本（带小版本）、sql_mode、语句里出现的特征关键词。
版本决定哪些方案存在——给 5.7 的服务器提 hash join、CTE、函数索引是错答案，不是次优答案。
方案里凡是有版本门槛的，必须标注小版本。

## 阶段二：解析 SQL 特征（信号 → 检查 → 策略）

执行计划用 {{tool:plan}} 取，拿到计划再分析。没有计划不下结论："缺个索引"这种文本
层面的判断，真实计划里往往是隐式类型转换、或者范围条件把复合索引截断了。

逐行比对下表，命中的信号全部列出，不要只挑最显眼的一条：

| 信号 | 检查 | 策略 |
| --- | --- | --- |
| `SELECT *` | 多余列传输 | 列裁剪 |
| `filesort` | EXPLAIN Extra 含 Using filesort | 索引优化 / 排序优化 |
| `temporary` | EXPLAIN Extra 含 Using temporary | 避免临时表 |
| `type=ALL` | 全表扫描 | 添加索引 |
| `type=index` | 索引全扫描 | 优化 WHERE 条件 |
| `key_len` 过大/过小 | 索引长度不合理 | 调整索引列 |
| Using index condition | ICP 生效 | 进一步优化 |
| `OR` 条件 | WHERE a=1 OR b=2 | UNION 改写 |
| `NOT IN` | 子查询 | NOT EXISTS 改写 |
| LIMIT 大 offset | 深度分页 | 游标分页 |
| LIKE '%x' | 前缀模糊 | 全文索引 |
| JOIN 无索引 | Bucket NL | 添加被驱动表索引 |
| COUNT() 大表 | 全表扫描 | 覆盖索引 / 近似值 |

## 阶段三：匹配策略链

一个特征拉出一条按代价排序的策略链：

策略 A 索引优化（主推，不改代码）→ 策略 B SQL 改写（次选）→ 策略 Z 参数或表结构调整（最后）。

A→Z 是优先级从高到低。先给 A，别拿 Z 当主推。

优化规则与技巧从知识库检索：{{tool:knowledge}}。报告里不引用非官方来源，只保留官方文档 URL。

## 阶段四：六段优化报告

产出固定六段，段名照抄，不合并、不改顺序：

**一、SQL语句** —— 格式化后的 SQL + 涉及的表 / 关键谓词 / 当前索引使用情况
**二、SQL特征分析** —— 命中的特征 + 严重度（🔴 / 🟡 / 🟢）+ 这个特征在 EXPLAIN 的哪个字段体现
**三、优化策略** —— 优先级 + 策略 + 具体操作 + 预期效果（量化：扫描行数从 X 降到 Y）
**四、优化流程** —— EXPLAIN → SHOW INDEX → 加索引 → 验证，写成可执行的步骤
**五、优化后SQL** —— 改写后的 SQL，附等价性说明（成立条件写清楚）
**附：等价性验证SQL** —— 改写有风险时给出验证 SQL；没有改写就写"本次无改写"

## 阶段五：SQL 等价改写校验

改写是这个流程唯一能造成数据错误的方式。**改写前**逐条过下面 14 项，每条标注
成立 / 不成立 / 未知：

| # | 检查项 | 不满足时的后果 |
| --- | --- | --- |
| 1 | NOT IN→NOT EXISTS：两侧关联列是否都 NOT NULL？ | NOT IN 遇 NULL 返回空集 |
| 2 | UNION→UNION ALL：是否确认分支间无重叠，或业务接受 bag 语义？ | UNION ALL 保留重复 |
| 3 | JOIN→EXISTS：右表是否至多一行匹配？ | JOIN 复制行，EXISTS 只判断存在 |
| 4 | LEFT JOIN ON→WHERE：是否确认未改变外连接补 NULL 行？ | 移动条件可能让 LEFT JOIN 退化 |
| 5 | 标量子查询→LEFT JOIN：右表连接键是否唯一（主键）？ | 标量多行报错，JOIN 静默复制 |
| 6 | COUNT(col)→COUNT(*)：col 是否保证 NOT NULL？ | COUNT(col) 不统计 NULL |
| 7 | SUM(CASE…END)→SUM(CASE…ELSE 0)：NULL 语义是否一致？ | ELSE 0 使 NULL 变 0 |
| 8 | 窗口函数 ORDER BY 增删：是否改变窗口帧？ | 默认窗口帧全量→累计 |
| 9 | 删除 CAST 类型转换：是否改变比较语义？ | 截断 / 舍入影响结果 |
| 10 | HAVING→WHERE：条件是否涉及聚合函数？ | WHERE 在聚合前过滤 |
| 11 | 删除内层 DISTINCT：是否改变外层重复行次数？ | 行倍数变化 |
| 12 | OR→UNION ALL 条件重叠：第二分支是否加了 IS NOT TRUE？ | 重叠行被重复输出 |
| 13 | 全局聚合 HAVING COUNT()>0：是否有 GROUP BY？ | 全局聚合一行为 0 需 HAVING |
| 14 | 用子查询 ORDER BY 替代最终 ORDER BY：顺序是否有保证？ | 子查询 ORDER BY 无序保证 |

有一条"不成立"就不推荐这条改写。有"未知"就把它写成成立条件，跟报告一起交出去，
不要当成已经成立。

改写完成后调 {{tool:validator}} 提交候选，入参是原始语句与改写后的语句。
它只登记候选，**调用成功不等于验证通过**——报告里不要把"已提交"写成"已验证"。

## 输出前强制检查

- **SQL 完整性**：报告里出现的每一条 SQL 都要过 {{tool:fullCheck}} 合规检查。
  一票否决——没过就不输出，先改到过为止。
- **等价改写校验**：改写后的 SQL 必须标注成立条件与验证方法，两样缺一不可。

## 证据门禁

这个流程带一道自动门禁：回合结束前会检查证据是否齐备。缺执行计划会被顶回来，
要求补齐后再给结论；知识检索、合规检查、改写提交缺失时会一并提醒，但不阻塞输出。

被顶回来时有两条正当出路，选一条，不要凭空补一份诊断：

1. 补齐缺的那一步，再给结论。
2. 如果卡在用户身上（还没拿到 SQL 原文、库表名、或者工具连不上），说明缺什么并结束本轮。
   工具连续失败时按流程写进"待补证据"那一节——写清楚要执行的语句、每条要看什么字段。

## 诊断命令

```sql
EXPLAIN FORMAT=JSON SELECT ...;           -- 详细执行计划
EXPLAIN ANALYZE SELECT ...;               -- 实际执行统计
SHOW PROFILE FOR QUERY N;                 -- 资源消耗
SELECT * FROM sys.statement_performance;  -- 性能视图
```
